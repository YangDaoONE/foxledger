# 3. M0｜保存后的聊天卡直接管理正式批次

## 3.1 要解决的问题

当前记账流程已经可以：

```text
用户输入
→ AI 候选
→ 核对
→ 确认
→ 正式保存
```

但保存以后，聊天里的 `LedgerResultCard` 主要负责显示“已保存”。

真正的：

- 查看正式账单；
- 修改单笔；
- 删除单笔；
- 撤销整批；

主要位于页面下方：

`RecentAiBatchesPanel`

这会导致同一次记账存在两个交互入口。

用户刚刚记完一批账后，最自然的行为应该是：

> 直接点刚刚这条狐狐回复里的“详情”。

而不是再向下寻找历史模块。

## 3.3 核心数据原则

### 未保存候选

事实源：

```text
ChatCandidateBatch.candidates
```

可以：

- 修改候选；
- 移除候选；
- 完成核对；
- 确认保存。

### 已保存并完成同步

正式前端事实源必须是：

```text
Dexie transactions_cache
current user
+
ai_batch_id
```

不能把：

- 保存前 candidate；
- 聊天内存中的旧金额；
- 保存时的 transaction snapshot；

当成正式账单真相源。

原则：

> 聊天卡是入口，Dexie 当前正式缓存是已保存批次的前端事实源。

当前代码中需要特别区分两个 ID：

```text
ChatCandidateBatch.id
```

只是在创建候选时生成的聊天内存 ID，不是正式 `ai_batch_id`，保存成功后也不会自动改成正式批次 ID。

正式详情必须使用：

```ts
batch.saveRequest?.batchId
```

只有当批次已经完成远端保存、`saveRequest.batchId` 存在且当前缓存可用时，才允许打开正式详情。不得把 `ChatCandidateBatch.id` 当成 `ai_batch_id`，也不得根据 `transactionIds` 重新拼出批次。

## 3.4 sync_warning

如果：

```text
Supabase 写入成功
Dexie refresh 失败
```

继续保持现有：

`sync_warning`

聊天卡显示：

```text
已保存 · 待同步

账单已经保存，但本地缓存暂时没有刷新成功。

[重新同步]
```

此时：

- 不能重新出现“确认记账”；
- 不能再次 insert；
- 不要使用过期 Dexie 数据开放正式编辑；
- 重新同步成功后，才开放正式“详情”。

不新增额外 Supabase detail query。

同样的原则也适用于正式编辑、单笔删除或整批撤销后的缓存刷新失败：

- 远端操作成功不能重新执行；
- 页面必须统一进入“正式操作已完成，但本地缓存待同步”的只同步状态；
- 聊天详情和 `RecentAiBatchesPanel` 都暂停新的正式写操作；
- 用户点击“重新同步”时只调用 `refreshAfterWrite()`；
- 同步成功并由 Dexie 重建批次后，两个入口同时恢复。

这个“缓存已过期”状态必须由同一个页面级管理实例持有，不能由两个入口各自保存一份互不相知的布尔值。

## 3.5 正式批次读取

当前现有模块已经提供：

```text
src/features/chat/recentAiBatches.ts
```

以及可直接复用的单批读取函数：

```ts
getRecentAiBatch(
  userId,
  batchId,
): Promise<RecentAiBatch | null>
```

V3.2 不新增 `aiBatchDetails.ts`，也不再创建同义的 `getAiBatchById()`。

要求：

- 只读 Dexie；
- 显式限制当前 `user_id`；
- 按 `ai_batch_id` 查询；
- 使用现有 recent batch 相同聚合规则；
- 不读取 `raw_text`；
- 删除一笔后数量与金额自动重算；
- 找不到时返回 `null`。

不要在 `LedgerResultCard` 内写第二套 batch grouping。

在 `src/app/queryKeys.ts` 增加单批详情 key，并继续挂在现有批次根 key 下：

```ts
recentAiBatch: (userId: string, batchId: string) =>
  [...queryKeys.recentAiBatches(userId), "detail", batchId] as const
```

这样现有 `refreshAfterWrite()` 对 `queryKeys.recentAiBatches(userId)` 的失效处理可以同时刷新：

- 最近批次列表；
- 当前聊天卡摘要；
- 已打开的正式批次详情。

不要另建一套手动事件总线，也不要在组件间复制金额和数量。

## 3.6 正式详情组件

建议新增：

```text
src/features/chat/SavedBatchDetailSheet.tsx
```

只负责**已保存正式账单**。

候选继续使用现有：

```text
BatchDetailSheet.tsx
```

两者不要混成一个组件，因为：

- candidate 是内存 draft；
- saved transaction 是正式数据库数据；

语义完全不同。

正式详情通过 `getRecentAiBatch()` 的 Query 数据渲染。它不接收保存前候选或保存时快照作为详情数据。

如果状态已经是 `saved`，但当前 Dexie 暂时查不到该批次：

- 不回退显示候选数据；
- 不开放编辑、删除或撤销；
- 显示“暂未在本地缓存中找到这批账单”；
- 提供只执行同步的“重新同步”。

这是缓存可用性问题，不代表可以重新保存候选。

## 3.7 复用正式管理逻辑

当前 `RecentAiBatchesPanel` 已经实现：

- `updateTransaction`
- `deleteTransaction`
- `deleteTransactionsByIds`
- `refreshAfterWrite`
- stale cache 处理
- 二次确认
- undo state
- focus restore

V3.2 只抽取“正式写入与写后同步”这一条业务链，例如：

```text
src/features/chat/useAiBatchManagement.ts
```

这个 hook 在 `ChatPage` 中只创建一次，再把同一个管理实例传给：

```text
RecentAiBatchesPanel
SavedBatchDetailSheet
```

不要让两个组件分别调用两次 hook。否则某一入口远端写成功但同步失败后，另一个入口仍可能基于旧缓存继续写。

共享管理实例只负责：

- 当前是否允许正式写操作；
- 当前正在执行的 action key；
- `updateTransaction` / `deleteTransaction` / `deleteTransactionsByIds`；
- 远端成功后的 `refreshAfterWrite()`；
- 写后同步失败时锁定两个入口；
- “重新同步”只刷新缓存，不重放远端写操作；
- 观察现有 `syncMeta.last_successful_sync_at`，无论用户从页面级提示还是现有同步状态条重试，只要出现晚于失败前基线的成功同步，就解除缓存过期锁；
- 整批撤销时调用现有 Chat undo action。

它不负责：

- 最近批次分页；
- `<details>` 展开状态；
- 当前打开哪个弹层；
- 候选编辑；
- 复制一份 batch 数据到本地 state。

这些表现状态继续留在对应页面或组件，避免把一个小改动做成新的全局 Provider。

提示信息也不要全部集中：

- 普通编辑/删除成功或远端失败，由发起操作的组件就近显示；
- 写后缓存刷新失败属于两个入口的共同阻断，由 `ChatPage` 只渲染一次页面级待同步提示；
- 初次保存产生的 `ChatCandidateBatch.sync_warning` 继续由原聊天卡自己显示，两者不要改成同一种新状态。

禁止复制两份完整：

```text
remote write
→ remoteSucceeded
→ refreshAfterWrite
→ sync warning
```

逻辑。

推荐调用关系：

```text
ChatPage
→ 创建一次 useAiBatchManagement()
→ RecentAiBatchesPanel 使用同一实例
→ SavedBatchDetailSheet 使用同一实例
```

正式操作统一执行：

```text
校验 online / 非 syncing / 非 busy / 缓存未过期
→ 执行一次远端 update 或 delete
→ 记录远端已成功
→ refreshAfterWrite
→ 现有 recentAiBatches 根 query 统一失效
→ 列表、聊天摘要、详情从 Dexie 重新读取
```

如果刷新失败：

```text
保留远端成功结果
→ hasStaleCacheAfterWrite = true
→ 记录失败前的 last_successful_sync_at
→ 两个入口禁用新的正式写操作
→ 只提供 retryCacheSync
```

不要只在 `retryCacheSync()` 的局部成功分支清除锁，否则用户通过现有同步状态条重试成功后，AI 批次管理仍会错误地保持禁用。

禁止复制两份这条流程，也不要为它增加新的 Context 或事件总线。

## 3.8 LedgerResultCard 调整

保存前行为基本不变。

保存成功后：

删除当前类似：

> 当前正式状态请以下方最近 AI 批次为准。

这种引导。

改为：

```text
已经记好了，共 2 笔。
```

并提供：

```text
[详情]
```

详情按钮必须属于当前这条聊天结果。

`LedgerResultCard` 的职责保持轻量：

- 保存前继续从 `batch.candidates` 渲染候选；
- 保存后用 `batch.saveRequest.batchId` 和单批 Query 读取正式摘要；
- 正式摘要只使用 `RecentAiBatch.transactionCount/expense/income/transactions`；
- 点击详情只把正式 `batchId` 交给 `ChatPage`；
- 不在卡片内执行 update/delete/undo；
- 不把保存前候选作为正式摘要的 fallback。

`sync_warning`、正式批次暂未读到或页面级 `hasStaleCacheAfterWrite` 为真时，卡片可以说明账单已保存，但必须隐藏或禁用“详情”，只开放重新同步。

`编辑`

SavedTransactionEditor

## 3.10 正式单笔删除

继续二次确认。

文案：

```text
删除这笔账单？

删除后无法恢复；本次记账的合计会按剩余账单重新计算。
```

删除后：

- 当前 batch 数量减少；
- 收入/支出合计重算；
- 当前聊天卡更新；
- Recent AI batch 更新。

如果删除最后一笔：

当前聊天 batch 进入：

`undone`

即可，不额外新增状态。

当前 reducer 的 `mark_batch_undone` 只接受 `undoing`。V3.2 需要做最小调整：

- 整批撤销仍保持 `saved/sync_warning → undoing → undone`；
- 单笔删除前若当前正式 Dexie batch 只有 1 条，远端删除成功后允许该 batch 从 `saved → undone`；
- 两种情况都必须按 `message.batch.saveRequest?.batchId` 匹配聊天消息；
- 不得按 `ChatCandidateBatch.id` 匹配；
- 单笔删除失败时保持原状态；
- 不新增 `deleted` 等同义状态。

删除非最后一笔时不修改 Chat reducer 中的候选或旧 transaction IDs；摘要由刷新后的 Dexie 批次自动重算。

## 3.11 整批撤销

正式详情底部：

```text
[撤销这一批]
```

必须使用**当前 Dexie batch 中仍存在的 transaction IDs**：

```ts
deleteTransactionsByIds(
  user.id,
  currentBatch.transactions.map(item => item.id),
)
```

不能只依赖保存时旧 ID 集合作为当前 UI 真相。

原因：

可能已经单独删除过其中一笔。

点击二次确认时，以当时 Query 返回的 `currentBatch` 生成一次待删除 ID 快照，并立即锁定管理操作。执行过程中不要再从保存时 `batch.transactionIds` 取值，也不要在失败后用新 ID 自动重试删除。

撤销成功：

- 当前聊天卡 → `已撤销`
- Recent AI batches 不再显示该 batch
- 其他 batch 不受影响。

如果远端撤销已经成功但缓存刷新失败：

- 聊天卡仍按远端成功结果显示“已撤销”；
- 页面显示“本地缓存待同步”；
- `RecentAiBatchesPanel` 暂停新的正式写操作；
- 重新同步只刷新 Dexie，不能再次调用整批删除。

## 3.12 ChatPage 状态

当前已有：

```text
selectedCandidate
```

增加一个轻量的正式批次弹层状态。推荐使用单个 discriminated union，避免多个布尔值组合出两个弹层同时打开：

```ts
type SavedBatchDialog =
  | { kind: "detail"; batchId: string }
  | { kind: "edit"; batchId: string; transactionId: string }
  | { kind: "delete"; batchId: string; transactionId: string }
  | { kind: "undo"; batchId: string }
  | null;
```

要求：

- candidate sheet 与 saved batch sheet 不能同时打开；
- 正式详情、`SavedTransactionEditor` 和 `ConfirmActionDialog` 任一时刻只能渲染一个；
- 从详情进入编辑或确认时，替换当前弹层内容，不在 `SavedBatchDetailSheet` 上叠第二个 `useModalDialog`；
- 弹层 state 只保存 `batchId` / `transactionId`，交易内容每次从当前单批 Query 解析，不保存 `CachedTransaction` snapshot 作为正式事实；
- 取消编辑或确认后回到同一 batch 详情；
- 操作后 batch 仍存在则回到刷新后的详情，已不存在则关闭整条详情流程；
- 整条流程保留最初“详情”按钮的 trigger ref，最终关闭后恢复焦点；
- 不改变现有 ChatSessionProvider 生命周期。

现有 `useModalDialog` 每个实例都会独立处理 Escape、焦点圈定和 body 滚动锁，因此禁止同时挂载嵌套 modal。这是单层弹层的原因，不需要为 V3.2 引入 modal manager。

## 5.5 Composer 自动增高

目标：

- 最少约 2 行；
- 最多约 5 行；
- 输入增加时自动长高；
- 删除内容后自动缩回；
- 超过最大高度后 textarea 内滚动。

不要安装第三方 autosize 库。

使用原生 textarea `scrollHeight`。

`ChatComposer` 增加一个 `textareaRef`，保留 `rows={2}` 作为无脚本和初始布局基线。文本变化后在 layout effect 中执行同一个轻量 resize 函数：

```ts
function resizeTextarea() {
  const textarea = textareaRef.current;

  if (!textarea) {
    return;
  }

  textarea.style.height = "auto";
  const maxHeight = Number.parseFloat(
    window.getComputedStyle(textarea).maxHeight,
  );
  const nextHeight = Number.isFinite(maxHeight)
    ? Math.min(textarea.scrollHeight, maxHeight)
    : textarea.scrollHeight;

  textarea.style.height = `${nextHeight}px`;
  textarea.style.overflowY =
    Number.isFinite(maxHeight) && textarea.scrollHeight > maxHeight
      ? "auto"
      : "hidden";
}
```

`text` 清空或删除内容时也会执行，因此输入框会自动缩回。不要在每次输入时创建 observer，也不要引入第三方 autosize 依赖。

CSS 配合：

```text
box-sizing: border-box
min-height: 约 2 行正文 + 现有上下内边距
max-height: 约 5 行正文 + 现有上下内边距
overflow-y: auto
resize: none
```

行高和上下内边距由 CSS 定义，JS 从计算后的 `max-height` 读取像素值；不要在 TS 中再维护另一组“5 行高度”常量。

## 5.6 Enter / Shift+Enter

物理键盘：

```text
Enter
→ 发送

Shift + Enter
→ 换行
```

仍需满足：

- 有文本；
- online；
- 非 parsing。

键盘发送和发送按钮必须复用当前同一个 `handleSubmit()`，不能分别维护两套 trim、online 和 parsing 判断。

`textarea` 的 `onKeyDown` 只拦截无修饰的 Enter：

```ts
if (event.key !== "Enter" || event.shiftKey) {
  return;
}

if (
  event.nativeEvent.isComposing ||
  composingRef.current ||
  event.nativeEvent.keyCode === 229
) {
  return;
}

event.preventDefault();
handleSubmit();
```

Shift+Enter 不调用 `preventDefault()`，让 textarea 保持浏览器原生换行行为。发送按钮继续走 form submit，不改变移动端点击路径。
