# FoxLedger V3.3 PR — 紧凑对话结果与多账本

## 0. PR 信息

**目标版本：** V3.3
**基线：** 当前 `YangDaoONE/foxledger` `main`，V3.2 已部署，后续视觉重整提交已进入生产
**适用范围：** FoxLedger Web/PWA + Supabase migrations + Supabase Edge Functions
**实施方式：** Codex 基于当前仓库增量修改

**本 PR 只做三件事：**

- M0：已保存记账结果 3 秒后自动收起为一行聊天消息，可随时展开
- M1：问账结果改成“回答先行 + 折叠详情”，与 M0 共用同一套折叠视觉语言
- M2：建立真正的多账本能力，并允许记账时选择目标账本

本 PR **不要求也不允许**顺手实现以下能力：

- 不做“用嘴修改刚才候选”
- 不做问账 stale/过期标记
- 不做自定义分类
- 不做账户/支付方式管理
- 不做多币种
- 不做 OCR
- 不做语音
- 不做离线正式写入队列
- 不做长期聊天持久化
- 不做宠物养成
- 不重写现有 V3.1 安全问账架构
- 不降低现有 RLS、publishable key、NetworkOnly、AI 确认后写入等安全边界

# 3. M0 — 已保存记账结果自动收起

## 3.1 目标

解决当前保存完成后大面积 `LedgerResultCard` 长期占据聊天区域的问题。

**只有真正完成保存且正式缓存可读的结果才自动收起。**

以下状态继续保持展开：

```text
draft
needs_attention
saving
sync_warning
error
```

以下状态使用紧凑展示：

```text
saved
undone
```

## 3.2 3 秒自动收起规则

当一个 batch 从其他状态**首次进入 `saved`**，并且当前正式 `savedBatch` 已经从 Dexie 成功读到：

```text
完整保存卡继续显示 3000 ms
↓
自动收起成一行
```

注意：

- 3 秒从“正式保存状态可展示”开始，不从用户点击“确认记账”瞬间开始。
- `sync_warning` 不开始倒计时。
- 如果同步失败，必须让“重新同步”按钮继续可见。
- 重试同步成功并重新进入正常 `saved` 后，可以重新触发一次 3 秒展示。

### 不需要持久化折叠状态

聊天本身就是内存会话。

推荐使用组件本地展示状态 + 前一状态 ref：

```text
draft → saved
```

时才触发 3 秒 timer。

如果组件重新 mount 时 batch 已经是 `saved`：

```text
默认直接折叠
```

避免用户切去其他页面再回来时又重复出现 3 秒大卡。

不要为了这个 UI 状态新增数据库字段。

## 3.3 用户交互优先于自动收起

如果用户在 3 秒内：

- 点击卡片
- focus 卡片中的按钮
- 点击“详情”
- 手动切换展开状态

则**取消当前自动收起 timer**。

不能出现：

> 用户正准备点击详情，卡片突然在手下折叠。

如果用户已经打开 `SavedBatchDetailSheet`，当前聊天卡保持用户主动选择的状态。

## 3.4 紧凑行视觉

紧凑状态必须像一条真正的 assistant 消息，而不是缩小版统计卡。

推荐：

```text
┌────────────────────────────────────────────┐
│ ✓  已记录 1 笔 · 支出 ¥40             ˅  │
└────────────────────────────────────────────┘
```

要求：

- 高度约 44–52px
- 左侧小型成功图标
- 主文案一行
- 右侧 Chevron
- 整行可点击
- `aria-expanded`
- 触控区域 ≥ 44px
- 文字过长时 ellipsis，不横向撑页面
- 与用户橙色聊天气泡形成明确左右层级
- 不再显示三块大金额卡，除非展开
- 不增加新的重型 UI 库

### 文案规则

仅支出：

```text
已记录 2 笔 · 支出 ¥65
```

仅收入：

```text
已记录 1 笔 · 收入 ¥8000
```

收入 + 支出：

```text
已记录 3 笔 · 支出 ¥120 · 收入 ¥8000
```

仅转账或无法形成简单合计：

```text
已记录 2 笔
```

M2 完成以后可以在右侧 Chevron 前加入一个小账本标签：

```text
已记录 2 笔 · 支出 ¥65      [旅行] ˅
```

窄屏时账本标签允许省略或 ellipsis，不能破坏单行结构。

## 3.5 展开状态

点击紧凑行后：

```text
ChevronDown → ChevronUp
```

下面展开**现有正式保存卡内容**。

不要复制新的“详情/编辑”实现。

展开内容继续使用：

- Dexie 当前正式 batch
- 现有统计摘要
- 现有“详情”
- `SavedBatchDetailSheet`
- `useAiBatchManagement`

即：

> 折叠只改变 presentation，不改变正式账单真相源。

## 3.6 `undone` 行为

整批撤销后不需要重新展开一个大卡。

紧凑行改成：

```text
✓ 这次记录已撤销
```

可以保留 Chevron 用于查看只读撤销状态，也可以无 Chevron。

不要再显示不存在的正式交易详情。

## 3.7 推荐共享组件

建议新增一个轻量的：

```text
src/features/chat/ChatResultDisclosure.tsx
```

或等价组件。

职责只包含：

- compact header
- expand/collapse
- Chevron
- `aria-expanded`
- 可选 auto-collapse
- reduced-motion
- 子内容容器

不要把：

- Supabase
- Dexie
- batch management
- query plan

塞进这个展示组件。

推荐 API 思路：

```tsx
<ChatResultDisclosure
  compactContent={...}
  defaultExpanded={...}
  autoCollapseMs={3000}
>
  ...
</ChatResultDisclosure>
```

具体 props 可由 Codex 根据现有组件风格调整，不要求照抄。

## 3.8 动效

前端必须好看，但保持轻量。

推荐：

- 收起/展开 160–220 ms
- opacity + translateY 轻微变化
- Chevron rotate
- 不使用夸张弹簧
- 不使用 JS 大型动画库
- `prefers-reduced-motion: reduce` 时立即切换

可以在保存成功的绿色提示条底部增加极细的 3 秒进度线，但不是必须项。

**不要显示跳动的 “3、2、1” 数字倒计时。**

## 3.9 滚动稳定性

自动收起后不能：

- 页面突然跳到顶部
- Composer 抖动
- 把用户当前正在看的旧消息推走
- 触发 ChatMessageList 强制滚动

重点在 Pixel 7 / PWA standalone 回归。

如果用户当前在消息底部：

- 收起后保持接近底部

如果用户已经向上滚动阅读旧消息：

- 不强制拉回最新消息。

## 3.10 M0 主要文件

预计：

```text
src/features/chat/ChatResultDisclosure.tsx        新增（推荐）
src/features/chat/LedgerResultCard.tsx
src/features/chat/ChatMessageList.tsx
src/styles/globals.css
```

必要时补：

```text
src/features/chat/ChatExperience.test.tsx
```

不要改数据库。

## 3.11 M0 验收

必须覆盖：

1. 保存成功后完整卡保持约 3 秒。
2. 3 秒后自动变成一行。
3. 点击箭头可以再次展开。
4. 展开后“详情”仍然进入现有正式 Batch Detail。
5. 3 秒内用户互动会阻止突兀自动收起。
6. `sync_warning` 不自动收起。
7. `error` 不自动收起。
8. 已保存组件重新 mount 时默认紧凑。
9. 撤销后紧凑状态正确。
10. 320px 不横向溢出。
11. reduced motion 正常。

完成后运行：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

# 4. M1 — 问账结果改成聊天式折叠结果

## 4.1 目标

当前 `LedgerQueryResultCard` 的后台事实与统计逻辑是正确的，本次**不改问账计算架构**。

只调整信息展示层：

> 用户首先看到“问题的直接答案”，完整统计和依据放到展开区域。

## 4.2 使用和 M0 相同的视觉语言

优先复用：

```text
ChatResultDisclosure
```

如果强行共用组件会使代码复杂，可以拆成两个组件，但：

- 外观
- Chevron
- 收起/展开动效
- spacing
- focus
- aria

必须共用同一套 CSS / 设计 token。

不要出现两套长得差不多但行为不同的 disclosure。

## 4.3 问账默认紧凑

问账结果返回后，不需要先展示当前六指标大卡。

默认显示：

```text
狐狐：本月餐饮支出 ¥680，共 12 笔。        ˅
```

建议：

- 用 `result.answer.text` 作为主回答
- 一行或最多两行视觉截断
- 移动端优先一眼看到答案
- 不需要 3 秒自动收起，因为它一开始就是紧凑回答

如果自然语言回答不可用：

```text
统计已经完成，点开查看结果。               ˅
```

## 4.4 展开后第一层仍是“回答”，不是六格统计

展开顺序：

```text
1. 自然语言答案
2. 当前问题真正请求的主要指标
3. 打开匹配账单
4. 更多统计（折叠）
5. 查看依据（折叠）
```

## 4.5 主要指标根据 Query Plan 决定

当前每个 operation 固定显示：

```text
支出
收入
结余
账单数
日均支出
最大支出
```

V3.3 改为：

> `operation.metrics` 请求什么，就优先展示什么。

建议抽一个纯函数：

```text
getPrimaryQueryMetrics(operation, operationResult)
```

映射：

```text
count                 → 账单数
expense               → 支出
income                → 收入
balance               → 结余
average_daily_expense → 日均支出
max_expense           → 最大支出
```

例如用户问：

> 这个月麦当劳花了多少？

plan metrics 如果只有：

```text
expense
count
```

主区域只显示：

```text
支出 ¥186
账单数 5
```

不要同时占据屏幕显示：

```text
收入
结余
日均
最大支出
```

## 4.6 “更多统计”

现有六项完整统计不要删除。

移入：

```text
<details>
  <summary>更多统计</summary>
</details>
```

展开以后仍能看：

- 支出
- 收入
- 结余
- 账单数
- 日均支出
- 最大支出

这样不损失能力，只调整信息优先级。

## 4.7 Compare / 多 operation

如果 query plan 有多个 operation：

- compact header 优先显示自然语言总回答
- 展开后每个 operation 仍分块
- 每块只先显示其 requested metrics
- compare range 继续显示
- 不删除现有 comparison 数据

不要为了“更简洁”丢掉完整问账依据。

## 4.8 “打开匹配账单”

保持现有：

```text
打开匹配账单
按可用条件打开账单
```

逻辑。

M2 加入多账本后，该跳转必须同时保持该问账结果对应的 `ledgerId`。

## 4.9 Evidence

保留：

```text
查看依据
继续显示依据
回答引用
```

以及：

- 最多 500 条 AI detail
- 正式统计覆盖全部匹配数据
- AI detail 截断不影响统计

本 PR 不修改这些安全契约。

## 4.10 M1 主要文件

预计：

```text
src/features/chat/ChatResultDisclosure.tsx
src/features/chat/LedgerQueryResultCard.tsx
src/features/chat/ChatMessageList.tsx
src/features/chat/LedgerQueryResultCard.test.tsx
src/styles/globals.css
```

不要修改：

```text

正式统计算法
grounded metric replacement
```

除非是为了类型适配且不改变语义。

## 4.11 M1 验收

必须覆盖：

1. 问账返回后默认是一条紧凑回答，不再是大统计报告。
2. 紧凑回答有 Chevron。
3. 展开后自然语言回答处于第一视觉层。
4. 主指标只展示 query plan 请求的 metrics。
5. “更多统计”仍能看到完整六项数据。
6. “打开匹配账单”功能不退化。
7. “查看依据”功能不退化。
8. compare query 不退化。
9. answer unavailable 有可理解降级。
10. 桌面 / Pixel 7 / 320px 视觉无溢出。

完成后运行：


# 5. M2 — 多账本

## 5.1 产品定义

V3.3 新增真正的：

```text
账本 Ledger
```

每一条正式 transaction 必须属于且只属于一个账本。

用户可以创建：

```text
日常账本
旅行账本
学习账本
工作报销
```

本版不支持“全部账本”统计模式。

应用始终有一个：

```text
当前账本 / active ledger
```

当前账本决定：

- 首页统计
- 账单列表
- 统计页
- 狐狐问账

但是：

> **记账时允许单独选择目标账本，不要求先切换当前账本。**

这是本需求的核心。

# 6. 多账本交互模型

## 6.1 全局当前账本

App Header 增加一个轻量 `LedgerSwitcher`：

```text
FoxLedger                [📒 日常账本 ˅]
狐狐记账
```

移动端可以：

```text
FoxLedger
狐狐记账       [日常账本 ˅]
```

要求：

- 不遮挡标题
- 320px 不溢出
- 名称过长 ellipsis
- 使用现有奶油/橙色设计系统
- 不做浏览器原生难看的大 select 作为最终主入口
- 可使用轻量 popover / bottom sheet
- 不引入大型 UI framework

账本切换只改变当前 scope，不产生远端写操作。

## 6.2 当前账本影响范围

当 active ledger = `日常账本`：

首页：

```text
只统计日常账本
```

账单页：

```text
只显示日常账本
```

统计页：

```text
只统计日常账本
```

狐狐问：

> 这个月花了多少？

只回答：

```text
日常账本
```

## 6.3 记账可以选择不同账本

### 手动记账

`TransactionForm` 增加必填：

```text
记入账本
[旅行账本 ˅]
```

默认值：

```text
activeLedgerId
```

但用户可以改为别的 ledger。

保存到旅行账本以后：

```text
active ledger 仍然保持原来的日常账本
```

不要自动切换页面 scope。

## 6.4 AI 记账

AI 返回候选以后，候选卡顶部增加：

```text
记入账本
[旅行账本 ˅]
```

规则：

- 默认当前 active ledger
- 用户确认前可以改
- **一个 AI batch 在 V3.3 只能属于一个 ledger**
- 不做“同一句话三笔分别进入三个账本”
- 不让 AI 猜账本
- `ledgerId` 是用户/UI 决定的结构化字段，不是模型自由生成字段

例如：

```text
用户：机票1200，酒店800

狐狐识别到 2 笔
记入账本：[旅行账本 ˅]

[确认记账]
```

确认后两笔 transaction 使用同一个 `ledger_id`。

## 6.5 Saved Compact Row

M0 紧凑结果在 M2 后可以显示目标账本：

```text
✓ 已记录 2 笔 · 支出 ¥2000     [旅行] ˅
```

账本名显示为小 badge。

不要让账本名称抢过金额主信息。

## 6.6 问账作用域

Chat 页面明显显示当前账本，例如 hero 下方轻量 chip：

```text
当前问账：日常账本
```

新问题：

> 这个月餐饮多少？

服务端只读取：

```text
current user
+
active ledger
+
query plan date/filter
```

不能把其他 ledger 数据混入。

# 7. 数据库设计

## 7.1 新表

新增 migration：

```text
supabase/migrations/005_add_ledgers.sql
```

建议新表：

```sql
public.ledgers
```

字段：

```text
id uuid primary key default gen_random_uuid()
user_id uuid not null default auth.uid()
name text not null
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

约束：

- `user_id -> auth.users(id) on delete cascade`
- name trim 后不能为空
- 建议 name 长度 1–30
- 同一用户不允许完全相同账本名
- 用户最多建议 20 个 ledger（UI/API 层限制即可）

使用已有 `set_updated_at()` trigger 或等价方式维护 `updated_at`。

## 7.2 给 transactions 增加 ledger_id

migration：

```text
transactions.ledger_id uuid
```

最终必须：

```text
NOT NULL
```

FK：

```text
references public.ledgers(id) on delete restrict
```

删除账本绝不能 cascade 删除交易。

## 7.3 现有数据迁移

migration 必须安全保留全部现有 transaction。

流程：

```text
1. 创建 ledgers 表
2. 给每个现有用户创建“默认账本”
3. transactions 增加 nullable ledger_id
4. 所有历史 transaction 指向各自用户的默认账本
5. 验证不存在 NULL / 跨用户 ledger
6. 再将 ledger_id 设为 NOT NULL
7. 加 FK / index
```

可以从 `auth.users` 为现有用户预建默认账本；至少必须覆盖所有现有 `transaction.user_id`。

不能丢失现有账单。

## 7.4 索引

建议：

```text
ledgers(user_id, created_at)
transactions(user_id, ledger_id, date desc)
transactions(user_id, ledger_id, created_at desc)
```

现有 AI batch index 保留。

# 8. RLS 与权限

## 8.1 ledgers RLS

`public.ledgers` 必须：

```text
enable row level security
```

用户只能：

- select own ledger
- insert own ledger
- update own ledger
- delete own ledger

所有 policy 依赖：

```text
auth.uid() = user_id
```

并与当前 transactions 权限风格保持一致。

## 8.2 transactions ledger ownership

只检查：

```text
transaction.user_id = auth.uid()
```

已经不够。

攻击者如果知道另一个用户的 ledger UUID，不能被允许把自己的 transaction 指向别人的 ledger。

因此 transaction INSERT / UPDATE policy 必须额外保证：

```text
ledger_id 属于 auth.uid()
```

可使用：

```sql
exists (
  select 1
  from public.ledgers
  where ledgers.id = transactions.ledger_id
    and ledgers.user_id = auth.uid()
)
```

或等价安全实现。

继续保持：

- 不使用 service_role
- 前端 publishable key
- Edge 用户 JWT
- 显式 `.eq("user_id", userId)`

# 9. 账本删除规则

V3.3 支持：

- 创建
- 重命名
- 切换
- 删除空账本

删除规则：

1. 最后一个账本不能删除。
2. 有正式 transaction 的账本不能删除。
3. DB FK 使用 `ON DELETE RESTRICT` 作为最终保护。
4. UI 必须给可理解错误：

```text
这个账本还有账单，不能直接删除。
请先处理其中的账单。
```

V3.3 不做：

```text
删除账本时自动级联删除账单
```

也不做：

```text
自动批量搬家
```

避免数据破坏。

# 28. 多账本验收场景

## Case 1：历史数据迁移

升级 migration 前有 100 条 transaction。

升级后：

```text
100 条全部仍存在
ledger_id 全部非空
全部属于当前用户的“默认账本”
金额/日期/分类不变
```

## Case 2：创建两个账本

创建：

```text
日常
旅行
```

刷新 / 重新登录后仍存在。

用户 B 看不到用户 A ledger。

## Case 3：当前账本 scope

active = 日常：

- Home 只算日常
- Transactions 只列日常
- Stats 只算日常
- Chat 问账只读日常

切换旅行：

全部变成旅行 scope。

## Case 4：手动记到非当前账本

active = 日常。

手动新增时：

```text
记入账本 = 旅行
```

保存后：

- transaction.ledger_id = 旅行
- active 仍然是日常
- 日常列表不出现这笔
- 切旅行后可见

## Case 5：AI 记到非当前账本

active = 日常。

用户：

```text
机票 1200
```

候选：

```text
记入账本 = 旅行
```

确认后：

- transaction 写旅行
- AI batch 全部相同 ledger_id
- compact row 显示旅行账本 badge
- active 仍然保持日常

## Case 6：AI batch ledger 一致性

一个 batch 3 笔。

任何写入路径都不能出现：

```text
2 笔 ledger A
1 笔 ledger B
同一个 ai_batch_id
```

validation 必须阻断。

## Case 7：问账隔离

日常本月支出：

```text
¥1000
```

旅行本月支出：

```text
¥5000
```

active = 日常。

问：

```text
这个月花了多少？
```

答案必须基于：

```text
¥1000
```

不能返回 ¥6000。

## Case 8：问账连续追问切 ledger

日常问：

```text
这个月餐饮多少？
```

切换旅行。

问：

```text
那上个月呢？
```

不得复用日常 previous context 造成跨账本语义污染。

## Case 9：Query Result Drilldown

旧消息属于日常账本。

后来 active 切为旅行。

点击旧消息：

```text
打开匹配账单
```

必须打开日常账本对应结果。

## Case 10：CSV

一次 CSV import：

```text
导入到旅行账本
```

所有合法行 ledger_id = 旅行。

## Case 11：删除账本

空账本：

```text
允许删除
```

有 transaction：

```text
UI 阻止
DB FK RESTRICT 再保护
```

最后一个账本：

```text
禁止删除
```

## Case 12：跨用户 ledger_id 攻击

用户 A 获取用户 B ledger UUID。

用户 A 尝试：

```text
INSERT / UPDATE transaction
ledger_id = B
```

必须被 RLS 拒绝。

## Case 13：离线

已缓存：

```text
日常
旅行
```

离线：

- 可以切换查看两本账
- Home/Transactions/Stats 按选择读取缓存
- 不能创建账本
- 不能重命名
- 不能删除
- 不能新增/编辑 transaction
- 不能 AI 问账/记账

# 38. V3.3 Done Definition

V3.3 只有同时达到以下体验才算完成。

### 对话记账

用户确认后看到成功卡。

约 3 秒以后，它自然变成：

```text
✓ 已记录 1 笔 · 支出 ¥40     [日常] ˅
```

聊天不再被永久的大卡占满。

想改账时：

```text
点箭头
→ 展开
→ 详情
→ 编辑 / 删除 / 撤销
```

### 问账

用户问：

```text
这个月餐饮花了多少？
```

第一眼看到的是：

```text
本月餐饮支出 ¥680，共 12 笔。 ˅
```

而不是六块统计卡。

需要更多信息时才展开。

### 多账本

用户当前浏览：

```text
日常账本
```

但可以在一次记账确认中选择：

```text
旅行账本
```

保存后这笔真正属于旅行账本，且：

- 日常统计不包含它
- 旅行统计包含它
- 问账严格按当前账本
- RLS 阻止跨用户 ledger
- 离线仍可切换已缓存账本查看

**这三个目标就是 V3.3，不额外扩张范围。**
